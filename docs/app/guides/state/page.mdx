# Noēsis State v1

Noēsis now persists a structured `state.json` alongside every episode. It captures the canonical cognitive loop so policies, evaluators, and tooling share the same view of what happened.

```text
Task → Observe → Interpret → Plan → Act → Reflect → State write → Learn
```

The core runner writes the state; policies only consume it. When a learn proposal is accepted, the resulting policy diff is recorded separately, keeping the state artifact immutable and audit-friendly.

<Callout type="info" emoji="🧭">
State is authored in raw JSON (no prompt formatting) and is scoped to a single episode. The core runner is the sole writer; policies can propose changes through direction events, but they never mutate `state.json` directly.
</Callout>

## State JSON layout (at a glance)

| Field | Description |
| --- | --- |
| `version` | Backwards-compatible identifier (currently `1.0`). |
| `state_schema_version` | Semantic version for the schema contract (initially `1.0.0`). |
| `episode` | Episode metadata: ID, seed, tags, adapter label, timestamps. |
| `goal` | The task the agent is pursuing plus optional context. |
| `beliefs` | Normalised statements the system inferred (with confidence + provenance). |
| `plan` | Ordered `steps[]` describing detector → action → verify progress. |
| `memory` | Persistent facts and scratchpad text captured during the run. |
| `outcomes` | Final status, action log, metrics (e.g., `task_score`), and artifacts. |
| `plan.steps[].inputs|outputs` | Optional payloads adapters may store for richer replay. |
| `outcomes.actions[]` | Individual decision points, including tool invocations. |

Plan steps use a controlled vocabulary (`kind ∈ {detect, analyze, plan, act, verify, review}`, `status ∈ {pending, running, done, skipped, failed, vetoed}`) so dashboards can render intent and execution consistently. Outcome statuses map to `{ok, error, vetoed, aborted, partial}` plus the transient `pending` state while a run is in flight.

<Callout type="warning" emoji="📄">
Schema migration note: v1 is the initial release. Fields may expand, but existing keys will remain stable. Use the `state_schema_version` field to gate parser upgrades.
</Callout>

## Episode index patterns

The `EpisodeIndex` keeps a JSONL manifest of prior runs (plus an optional FAISS index for similarity search). Expired episodes are hidden from default iterators but never removed unless you call `vacuum()`.

Retrieve the most recent matching episodes:

```python filename="python"
from noesis.episode import EpisodeIndex

store = EpisodeIndex("./runs/_episodes")
latest = [rec for idx, rec in zip(range(5), store.iter())]
```

Filter by adapter label before slicing:

```python filename="python"
recent_incidents = [
    rec
    for rec in store.iter()
    if rec.using == "adapter:incident"
]
```

Perform similarity lookup when you persist embeddings alongside the manifest:

```python filename="python"
matches = store.search(embedding=[0.05, 0.1, 0.02], k=3)
for episode_id, distance in matches:
    ...
```

Control retention explicitly:

```python filename="python"
store = EpisodeIndex("./runs/_episodes", ttl_days=14)
store.vacuum()  # permanently drop records whose TTL has passed
```

## How policies use State

Intuition and direction policies receive the state snapshot inside their advisory hook. You can rely on the following fields:

- `goal.task` / `goal.context` describe the objective and any operator-provided framing.
- `plan.steps` lists the latest plan (IDs, kinds, rationale) you can patch or veto.
- `memory.facts` gives you normalised telemetry (each fact includes timestamps and provenance).
- `outcomes.actions` records tool invocations and adapter responses, enabling guardrails to detect risky patterns.
- `beliefs` reflects prior inferences so you can short-circuit duplicate work.

Policies should treat the snapshot as read-only. To steer execution, return hints, interventions, or vetoes through the policy API and let the core runner replay the resulting patch into the next `state.json` write.
